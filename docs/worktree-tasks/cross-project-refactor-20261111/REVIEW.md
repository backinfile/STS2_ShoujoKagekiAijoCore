# Core / Karen / Junna 审查结论与重构计划

## 结论

值得继续收敛的是流程重复和生命周期保护。Core 已承担闪耀、存档、选牌、复制、音乐和双版本适配；本轮进一步统一自定义选择同步，并修复角色临时移牌的异常恢复。角色数值、卡名、本地化与存档字段保持现有含义。

## 审查入口

- Core：Bootstrap 择版、Api.V1 兼容接口、Runtime 模型发现与初始化、Execution/Shine 结算与复制、配置和表现接入；同时检查遥测队列、服务端 Store/Handler、Web 与 SDK 的职责划分。
- Karen：入口、闪耀适配、约定牌堆、全局移牌、选项模型、遗物奖励、双版本兼容与角色打包。
- Junna：箭矢部署/复制/结算、手牌转箭矢、CardActions、知识关联/获得/成长、伤害来源与能力探测、卡面与连线、元数据生成和角色打包。
- 服务端、导出与表现的大型实现列入后续维护候选；本轮运行验证集中在实际修改的游戏流程。

## 保留的必要特殊处理

- Karen 旧闪耀字段、负哨兵、规则快照和来源身份兼容属于存档与旧包协议，应保留在 Core 迁移入口。
- Junna 知识获得来源的名单区分整组获得、选择、变形和发现。把它改成“任何获得都发整组”会改变当前机制。
- 临时复制、转交和重新获得拥有不同生命周期，继续通过 CardCopies 的用途参数表达。
- 箭矢部署和实际结算属于不同阶段，仍由角色调度与 Core 的实际结算入口协作。

## 后续简要计划

1. **箭矢复制牌效入口**：先补复制箭矢经过第三方路由、同步异常和不同接收玩家的回归，再设计可重新绑定目标卡牌的延迟牌效载体，替换 ArrowCombat.CopyAll 的反射 OnPlay 直调。
2. **知识成长规则表**：把 JK148、JK184、JK314 的主牌、成员、计数方式和上限集中成显式规则，统一 BindResearch / ResearchDepleted；保留已发布字段名及旧存档迁移。
3. **导出生命周期**：把 CardPngExportUtil 中的临时模型、视口、节点和渲染等待收敛为一次导出会话；文件索引与像素输出分开维护，用成功/异常两条路径核对像素和资源释放。
