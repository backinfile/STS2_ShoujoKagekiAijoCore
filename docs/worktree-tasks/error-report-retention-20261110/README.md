# 旧报错自动清理与巡检适配

## 原始输入

在本 Core 项目使用 $worktree-task 实现用户已经批准的旧报错自动清理，并完成必要的 Karen 每日巡检兼容适配。

## 相关用户原文

用户批准的是以下旧数据淘汰方案。

- 普通报错连续 7 天没有新增上报后，清理完整正文、调用栈和会话明细。
- 已忽略的问题连续 3 天无新增后清理。
- 待处理、待上线核验的问题加入保留名单，结案后再计保留期限。
- 保留轻量指纹摘要、累计次数和必要的重试去重信息，同时清除无引用的环境数据，并让每日巡检识别正常淘汰。

## 工作方式

先阅读本仓库 AGENTS.md、services/telemetry/README.md、deploy/telemetry/README.md，以及 $worktree-task。捕获起始检出、分支、提交和未提交状态，在 ../worktrees/<projectName>/<task-slug> 创建工作树。建议任务名为 error-report-retention-20261110。使用 UTF-8 和最小改动，修改与验证在工作树进行。

主实现目前位于 services/telemetry/error_reports.py、app.py、deploy/telemetry/install.py。核对最新源码归属后实现。相关 Karen 仓库为 <Karen仓库>。涉及该仓库的跟踪文件改动时，同样先读其 AGENTS.md 并创建独立工作树，保护主检出现有文档改动及忽略目录中的巡检状态。

合并与清理前，按 $worktree-task 要求向用户展示具体提交、验证及清理范围并取得确认。服务上线执行沿用项目的部署授权约定，交付上线步骤和清理预览结果。

## 已核实的背景

服务运行于现有 SSH 配置的 <生产SSH配置>，服务单元为 karen-observatory.service。生产数据、访问配置和凭据由既有部署配置读取，文档使用用途占位符。2026-11-10 15:06 的只读统计为 7,036 类错误、8,291 份报告，最早接收时间为 11-04 21:45。按当前记录中的最近事件或接收时间估算，连续 3 天不活跃的约 2,915 类，正文和调用栈约 7.4 MiB，7 天以上为零。这些数字用于背景，实施时重新预览并排除保留名单。

服务当前按指纹聚合，完整环境去重并 gzip 保存。error_reports 保存 report_id、session、group_id、累计 count、first_seen、last_seen、received，上传支持重复和乱序幂等。现有 received 仅为报告最初接收时间，需要为清理规则可靠记录服务端最近活动时间，覆盖同一报告的计数更新及历史日志补传。

Karen 的巡检配置和基线在主仓库 artifacts/error-watch/config.json、triage-policy.json、state.json，文档为 docs/待修复问题.md。2026-11-10 的采集脚本和审阅脚本在 artifacts/error-watch/2026-11-10/，它们属于忽略的本地材料。当前 pending_issue_ids 为空，fixed_awaiting_deployment_issue_ids 包含 OBS-008、009、010、013、033、034、035、036、037、038，人工忽略项 28 个。状态以开始实施时的最新策略和文档为准。

## 实现要求

1. 增加可配置的报错保留策略、每天运行的清理入口与定时任务。普通报错默认 7 天，明确忽略的默认 3 天。以服务端最后有效接收或更新活动计算期限，历史补传应获得相应保护。提供 dry-run，展示按原因分组的候选数量、正文大小估算和保留数量。
2. 将巡检中的保留与忽略结论可靠地对接服务端，按指纹应用。待处理和待上线核验记录获得优先保护。映射缺失、过期或同步失败时采用保守保留规则。结案后的保留期限从结案时间起计算。
3. 清理完整正文、调用栈、可淘汰的会话明细，以及确认已无引用的环境数据。轻量摘要和必要的去重状态用于历史累计、会话统计、旧 report_id 重试及复发识别。设计有效数据与已淘汰摘要的计数和容量口径，使清理实际释放活动分类容量。
4. 处理并发上传、执行中断和重复运行，使用一致的事务边界。清理后旧报告重试应保持幂等，新报告再次出现应正确恢复可观察状态，保留历史次数及首次、最近时间的含义。
5. 同步实现只读 API 的淘汰识别与 Karen 每日巡检兼容。当前采集脚本会断言历史指纹全部仍存在、计数单调增长。让完整分页采集、淘汰确认和本地基线更新区分正常淘汰与访问或分页失败，并保留稳定问题编号、人工状态和修复记录。给出可实际应用的本地巡检适配。
6. 清理结果记录删除、保留、失效环境、耗时和失败范围。按照实际空闲页情况提供受控空间回收安排。任务目标为旧数据生命周期管理。
7. 在隔离数据库执行与本次变更相关的最小必要回归，覆盖 3/7 天边界、计数续传、历史补传、保护/忽略状态、结案计时、重试幂等、复发、会话统计、无引用环境清理、并发或中断恢复及巡检兼容。生产数据只读评估，副本用于迁移和清理验证。
