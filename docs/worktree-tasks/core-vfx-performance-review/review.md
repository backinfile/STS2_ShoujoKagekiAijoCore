# Core 特效性能审查与优化

## 结论

已完成全部 Core 视觉入口的源码审查，并修复五类主要性能热点。临界手牌的重复状态分配和关键词查询、卡牌周转时重建大缓冲区、首次卡框解压以及耗尽动画的逐粒子提交均已优化。

双版本的常驻与预警持续绘制在本机 60 FPS 目标下具有余量。首次建牌和大量原生建牌／回池仍能出现长帧，此次最稳定的改善来自分配量和首次管线编译次数，具体帧间隔受背景、GC 与调度影响。

## 重构结果

| 基线热点 | 当前实现 |
| --- | --- |
| 每个特效各自持有并重建绘制数组 | 常驻、预警、耗尽共用线程内 scratch batch，Flush 同步复制有效几何，卡牌归池保留共享容量 |
| 每帧 GetState 创建 record，并重复查询原生关键词 Hook | 内部只读值类型视觉状态。关键词同帧复用，KeywordsChanged 立即失效，公开 GetState 保持原签名和结果含义 |
| Spark 使用引用类型逐次分配 | 固定容量 List 中存储值类型粒子，按原顺序更新和移除 |
| 首次显示新卡框同步解压 | 加载边界批量准备五类原生卡框，同源图集只读回、解压一次，临时 CPU 图像统一释放 |
| 轮廓强引用与空来源重复读取 | 弱键缓存，纹理 Changed 失效，空结果最多每 500 ms 自动重试，显式 Prepare 支持立即重试 |
| 耗尽每帧最多 129 次绘制 API 调用 | 轨迹预计算并批量提交三角形，复用 Add 材质 |
| 多张耗尽缺少总预算 | 同进程最多保留 160 个聚拢粒子。Full 每个最多申请 40 个，Reduced 最多 10 个，超额仍保留淡出、核心闪光、归池和到达反馈 |
| 祖先隐藏后仍模拟临界粒子 | 提前检查实际可见性，跳过隐藏卡牌的关键词查询、粒子和轮廓更新 |
| Core 独立首次绘制准备不完整 | 加载期预编译托管表现方法，在临时 SubViewport 完成两帧真实绘制并检查 Canvas 绘制量。Off 启动同样准备，覆盖随后首次开启。完成和失败路径均释放视口 |

160 个聚拢粒子预算和关闭档启动时预热是本次实现选择。普通单张耗尽保留完整粒子，批量超额时优先控制峰值。预热不创建卡牌模型，不调用牌效，不改变规则、随机数、牌堆或收益。

## 实机对照

正式版 v0.107.1，MegaDot 4.5.1 m.12。测试版 v0.111.0，MegaDot 4.5.1 m.14。BaseLib 3.4.7，RTX 4060，D3D12 Forward+，截图确认实际绘制为 1920 × 1080。

每帧主线程托管分配量如下，单位为 KiB。数值包含该采样窗口内的其他游戏工作。

| Full 场景 | 正式版，基线 → 最终 | 测试版，基线 → 最终 |
| --- | --- | --- |
| 10 张常驻闪耀 | 5.55 → 4.53 | 5.57 → 4.52 |
| 10 张临界预警 | 45.73 → 24.48 | 45.76 → 24.49 |
| 隐藏临界手牌 | 25.11 → 1.51 | 25.12 → 1.53 |
| 回池后重建手牌 | 25.17 → 17.50 | 76.38 → 54.69 |

临界预警两版约下降 46.5%，隐藏临界手牌约下降 94%。公开 API 程序集与基线逐字节一致。

| 首次 Canvas 管线编译增量 | 正式版，基线 → 最终 | 测试版，基线 → 最终 |
| --- | --- | --- |
| 首次创建 10 张手牌 | 2 → 1 | 3 → 2 |
| 反复打开牌堆 | 2 → 0 | 2 → 0 |
| 10 张同时耗尽 | 3 → 0 | 3 → 0 |

Full 临界手牌的 P99 帧间隔分别约为正式版 16.97 ms、测试版 17.44 ms。最终两版的持续场景中，探针记录的场景处理与一次强制绘制均值大多约 1.1–1.6 ms。

### 长帧与归因

- 正式版最终首次建牌窗口出现 87.95 ms 的帧间隔尖峰。该帧记录的场景处理约 1.19 ms、GPU 约 0.50 ms，GC 计数没有变化。现有轨迹未定位这段帧间间隔的原因，将它保留为未归因尖峰。
- 测试版最终同时耗尽窗口出现 69.79 ms 的帧间隔尖峰，位于 Gen0／Gen1 GC 计数变化附近。该帧场景处理约 1.00 ms、GPU 约 0.46 ms。首次耗尽 Canvas 编译增量为 0，仍保留整个游戏帧的 GC 长帧记录。
- 压力回池以“五轮清空并创建 10 张手牌”为一次操作，两次重复。Full 每帧分配从约 229 KiB 降到约 158 KiB，下降约 31%。CPU 均值、P99 和最大值在重复间波动，单次最大值不能作为稳定收益结论。Off 压力窗口也出现约 47–61 ms 最大帧间隔，说明整个原生建牌、移牌与回池流程仍需独立看待。

### 采样方法

- 基线源码提交为 `368f68c5c2d9fc2e03ebc6c6f5006952df9237ac`。基线与优化包各自在独立游戏进程中运行，通过 KarenSTS2MCP 启动原生战斗、触发测试命令和保存截图。
- 主对照共 84 个窗口，包括基线／最终包 × 双版本 × Full／Reduced／Off × 七种场景。七种场景为首次建手牌、常驻、临界、隐藏临界、牌堆开关、回池重建和同时耗尽。最终包额外以 Off 配置冷启动，然后在同一进程逐档测试。
- 正式版与测试版使用独立用户目录、日志及随机端口。silent_test=true、muted=false，最小化并禁止焦点。逐帧 ForceDraw 保证真实绘制，窗口监控未发现抢焦点，观察到的可见窗口样本均最小化。
- 帧间隔使用 Stopwatch 单调时钟，记录逐帧 CSV。场景处理指标从 ProcessFrame 到末尾探针完成一次 ForceDraw，包含大部分节点处理和该次绘制，帧末其他工作与等待不在这一指标内。
- 稳态窗口先等待 10 帧稳定。初轮使用引擎 delta 并混入界面切换边界的记录单独保留，最终表格使用重跑后的单调时钟数据。固定操作回池改为操作结束后停止采样，防止定时窗口截断不同数量的操作。
- 各轮新局种子未固定，原生背景和其他环境工作存在变化。GPU 均值和少量 CPU 差异按观察值保留，分配量、管线编译和生命周期断言作为主要依据。
- 原生铁甲战士卡牌通过 Core 正式 API 获得闪耀，测试窗口每组 10 张，实际结算通过共享 Arrow 结算入口提交一次预算。效果负载为空以隔离共享表现，原生模型与视图仍按真实结算路径清理。

## 验证结果

- 双版本最终发行构建通过，0 警告、0 错误，严格包校验通过。
- PresentationChecks 六项通过。覆盖空 Atlas、同来源恢复、默认区域、嵌套恢复、纹理变化失效和透明来源替换。
- 双版本 ResolutionChecks 通过，覆盖原生重放、额外 Effect 不扣预算、箭矢实际结算、异常传播和批次上下文释放。
- 最终双版本各 21 个性能窗口及各 10 项原生模型／视觉清理断言通过。
- 最终双版本各 11 项边界断言通过。包括同帧增加与移除 Eternal、同时耗尽预算不超过 160、提前退出归还预算和卡牌、动画中关闭特效、零余量保留、预热视口已释放。
- 测试版最终包的固定操作回池补充复测为 6 个窗口、6 项模型／视觉一致性断言，全部通过。
- 观察并查看了前后截图，临界手牌可见，清理后原生手牌区没有残留牌节点。每个测试进程在退出前核对实际 EXE 路径并停止。

初轮测试探针修正过 SDK 需求元数据、版本对应 MCP DLL 和采样边界。最终采用测试版引用在任务忽略目录重建 MCP，外部 MCP 仓库保持原样。无窗口渲染器中的 ImageTexture.Update/SetImage 像素重读实验未作为通过项，正式回归使用 Atlas 来源替换路径。

## 全部视觉入口覆盖

| 入口 | 结论 |
| --- | --- |
| 常驻闪耀、临界预警 | 本次重构与双版本实测的主要入口，单牌粒子上限仍为 14／40，Reduced 关闭常驻并降低预警密度 |
| 耗尽、到达反馈 | 本次重构及正常、提前退出、Off 中断实测。到达节点复用，冲击历史最多三次 |
| 牌堆装饰两分支 | 两分支源码审查，闪耀分支开关实测。动画最长 0.64 秒后停止 Process，之后保留静态命令 |
| 按钮计数、悬停、HSV | 源码审查，计数 Tween 先终止旧实例，悬停支持取消与有效性检查 |
| 长颈鹿启动画面 | 源码审查，一次旋转 Sprite 和背景，图片与音效同步加载处于启动阶段 |
| 音乐 UI、衍生牌标记和 HoverTip | 源码审查，UI 时钟每 0.15 秒更新，图标主要按交互重绘，标签按标题与配置更新 |
| 公共 CanvasGeometryBatch、LightRibbon | 源码审查并通过共享批次实机接入。Span 只提交有效范围，LightRibbon 复用线程内数组 |
| 图片导出 | 源码审查，显式导出命令包含 SubViewport、图像读回和磁盘工作 |

Reduced 的 20 次／秒限制作用于绘制命令重建，GPU 仍在后续帧使用保留命令绘制。GPU 压力的下降主要来自关闭常驻、降低粒子和曲线细分，而非将整个渲染器降到 20 FPS。[Godot CanvasItem 文档](https://docs.godotengine.org/en/4.5/classes/class_canvasitem.html)

加载阶段预演 2D 管线与实际绘制完成核验对应 Godot 首次 Canvas 编译机制。最终首次手牌窗口仍有 1／2 次 Canvas 编译增量，后续首次耗尽和牌堆装饰为 0。[Godot 管线编译文档](https://docs.godotengine.org/en/4.5/tutorials/performance/pipeline_compilations.html)
