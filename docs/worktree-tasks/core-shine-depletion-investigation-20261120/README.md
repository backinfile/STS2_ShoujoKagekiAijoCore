## 计划

从上一条记录的 0/3 永久「渴望」出发，使用含同版 Core、纯那与 MCP 的隔离游戏验证 Core 扣次和批次清理的边界，并核对现场日志与存档可以支持的结论。

## 结果

Core 有一条能重现永久牌组残留 0/3「渴望」的路径。自动出牌的异步任务可以继承已经关闭的父批次；Core 仍为这次出牌建立子批次，并在扣除最后一次闪耀时同步把永久原牌写到 0。子批次收尾将卡牌交给已经清理完毕的父批次，父批次不会再归档或移除这张原牌。

下一场创建战斗副本时，Core 将这张 0/3 原牌复制成空壳。[批次清理](../../../src/Modules/Shine/ShineService.cs#L105) · [永久来源更新](../../../src/Modules/Shine/ShineService.cs#L171) · [复制补丁](../../../src/Modules/Shine/ShineService.cs#L367)

现场两张第 6 层获得的「渴望」在获得记录中均为 3/3。一张已经归档，另一张随存档保留在永久牌组中，当前次数为 0，上限为 3，耗尽和待耗尽标记均为 false。现场日志没有卡牌实例、预算及批次状态，无法确认原局哪次出牌触发了已复现的边界。对局记录显示偷窃草蜢偷走并归还的是「星光迸发」，排除了它通过偷取并返还「渴望」形成该残留的路径。

## 定向复现

使用 v0.113.1、现场同版 Core 1.9.7 Beta Runtime 和纯那 Beta Runtime。用真实的「渴望」和 Core 的自动出牌入口复测，探针控制父批次关闭时机，两种场景均从 1/3 开始。隔离游戏通过 MCP 操作。

| 场景 | 实际结果 |
| --- | --- |
| 父批次等待子出牌完成 | 永久牌移除并归档一次 |
| 父批次先关闭，再放行子出牌 | 战斗牌进入消耗堆，原牌留在永久牌组。剩余 0/3，两个耗尽标记均为 false，没有新增归档 |
| 正常使用另一张闪耀牌击杀最后一只敌人 | 致胜牌的原牌正常清理。胜利存档仍保留异常的「渴望」 |
| 正常进入下一场战斗 | 一张由残留「渴望」生成的空壳进入起手，截图与模型来源吻合 |
