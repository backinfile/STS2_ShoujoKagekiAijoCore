# 两项问题的定向诊断

## OBS-033

真实 Godot 4.5.1.m.12 引擎读取未设置 Atlas 的 AtlasTexture，在生产 ReadImage 直接解引用 Atlas 的位置抛出 NullReferenceException，调用链与历史报告相符。成功读取前的空轮廓又被静态字典缓存，来源后续就绪也无法恢复。已加入来源检查、递归图像读取、默认区域轴尺寸处理，并只缓存成功生成的轮廓。

历史报告没有保留具体纹理，因此这里确认的是当前源码的同链失败边界，不能断言两个旧指纹的唯一输入都是空 Atlas。[Godot AtlasTexture 文档](https://docs.godotengine.org/en/4.5/classes/class_atlastexture.html)说明 atlas 可以嵌套，区域某轴尺寸为零时沿用来源尺寸。

原实现实际失败日志为 `out/tmp/core-observations/border-red.log`。同一检查修复后覆盖空来源、来源恢复、默认区域和嵌套来源恢复四项，全部通过。Stable 与 Beta 实际 Core 的 MCP 命令均返回 points=5、recovered=true，原生池初始化及真实卡面通过。

## OBS-036

失败回路使用真实 v0.111.0 游戏、BaseLib、MCP、Core 1.0.2 与强制绘制探针，在 Common 完整加载过程中出现一次原生 Invalid Task ID。观察栈命中 ScriptManagerBridge 的基类脚本装载；另外的同文本记录只有原生栈，不能用同一文本直接合并根因。

| 定向对照 | 实际结果 |
| --- | --- |
| Core 1.0.1，普通最小化启动，采集关闭／回环采集开启 | 各0次；未复现旧记录的3次 |
| Core 1.0.1，强制绘制 | 1次，后续脚本观察样本2次 |
| 移除 Core，保持同一绘制探针 | 1次；不是 Core 独占的原生问题 |
| 主线程先准备35个脚本基类 | 仍1次 |
| 仅让场景顺序加载 | 仍1次；完整792项，约7.5秒 |
| 预先加载 atlas 来源 | 仍1次 |
| 单个未完成资源加载 | 0次；完整792项，26,774毫秒 |
| 预先准备共享依赖，排除没有实际文件的虚拟 atlas 路径 | 0次及0新增引擎错误；完整792项 |
| 实际 Core 修复包，无实验调度注入 | 0次；193项依赖准备294毫秒，完整792项，Common约4.2秒 |
| 同步公共配置后的 Beta 完整组合 | 0次；完整800项，Common约4.1秒 |
| 同步公共配置后的 Stable 最小组合 | 0次；完整778项，Common约4.1秒 |

根因定位到 Common 共享依赖的并发／递归首次装载边界，等待时原生任务 ID 不存在。原生 WorkerThreadPool 的错误检查及 [Godot ResourceLoader 修复说明](https://github.com/godotengine/godot/pull/104060)提供了递归等待会使任务 ID 失效的机制依据；具体底层任务编号不由公开 API 暴露。修复只在 Common 会话构造前准备被多处引用的真实依赖，保留原并发批次、原始资源集合、引擎错误与回退路径。临时强引用在会话完成或构造失败时释放，不 Dispose 游戏共享资源。

实验中直接查询虚拟 .tres 的依赖会产生文本读取错误，该实验未计为通过，已经排除这些无实际文件的路径。用于判断的最终日志无该错误；实验调度和脚本预热均不在生产实现或最终游戏探针中。
